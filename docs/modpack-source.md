# 整合包源生态 (Modpack Source Ecosystem)

> 状态：**想法阶段** — 本文档记录设计意图与需求，不涉及实现细节。
> 待与作者整体过一遍后再细化为可落地的 spec。

## 1. 背景与动机

### 1.1 出发点

作者 (mickeymiao / 鄙人米奇喵) 长期在 B 站发布 Minecraft 整合包视频（材质 / mod / 整合包介绍），手中有约 2.5 万粉丝的内容创作渠道。当前的整合包分发方式是网盘 + 视频引流，存在几个痛点：

- 每个 MC 版本要重新打一份整合包并重新上传
- mod 上游更新后，玩家手上的整合包不能自动跟进
- 配置文件调整后，老用户拿不到新配置
- 内容创作（视频）和工具（启动器）是割裂的

### 1.2 战略机会

PCL2 / HMCL / Prism 三大启动器都没有做"开放整合包源生态"。Modrinth 的 mrpack 是静态快照，CurseForge 整合包同理。这个空白是 MMCL 找到差异化定位的最好机会：**把启动器从"工具"升级成"整合包平台"**。

- 内容方（米奇喵等 UP 主）维护一份 mod 列表声明
- 启动器订阅源、自动解算 mod 兼容性、自动安装、自动跟进更新
- 玩家拿到的不是一个静态包，而是一份"活的整合包"

### 1.3 为什么现在做

- MMCL 已经具备 70% 的基础能力：Modrinth/CurseForge 搜索安装、依赖解析、mod 更新检测、多下载源、mrpack 导入导出
- 需要补的是"远程清单 + 解算 + 升级流程 + CI 验证"，约 22 天工作量
- 作者粉丝群体（PC mod 玩家）和 MMCL 目标用户重合度极高，发布渠道天然成立

## 2. 核心概念

### 2.1 三层模型

```
┌──────────────────────────────────────────────┐
│  整合包源 (Source)                            │
│  ↓ 由内容作者维护，托管在 GitHub 等公开位置  │
│                                              │
│  ┌────────────────────────────────────────┐ │
│  │  整合包 (Pack)                          │ │
│  │  ↓ 一个 mod 列表 + 配置 overlay         │ │
│  │  ↓ 声明支持哪些 MC 版本                  │ │
│  │                                         │ │
│  │  ┌──────────────────────────────────┐  │ │
│  │  │  Mod 列表（声明式）                │  │ │
│  │  │  ↓ 不写死版本号                   │  │ │
│  │  │  ↓ 启动器在玩家选定 MC 版本后解算  │  │ │
│  │  └──────────────────────────────────┘  │ │
│  └────────────────────────────────────────┘ │
└──────────────────────────────────────────────┘
```

### 2.2 关键转变："静态快照"→"声明式定义"

| 维度 | mrpack（现有） | 米奇喵源（拟议） |
|---|---|---|
| 整合包绑定 | 1 个 MC 版本 + 写死 mod 版本 | 多个 MC 版本 + 只声明 mod ID |
| 新版 MC 出现 | 作者重打整合包 | 作者在 manifest 加一行版本号 |
| mod 上游更新 | 玩家手动更新 | 启动器自动跟进 |
| 配置调整 | 重发整合包 | overlay 推送 |
| 验证 | 无 | CI 自动跑 smoke test |

## 3. 用户角色与价值

### 3.1 整合包作者（如米奇喵）

**痛点**：
- 维护多个 MC 版本的整合包成本高
- mod 升级 / 弃坑后玩家手上的版本失效
- 配置文件改动很难触达老用户

**价值**：
- 维护一份声明，自动适配多个 MC 版本
- 推送 mod / 配置更新，玩家端自动同步
- CI 实时告警 mod 上游破坏整合包
- 作者数据反馈：哪些版本卡用户、哪些 mod 是关键阻塞

### 3.2 玩家

**痛点**：
- 想玩最新 MC 但要等整合包作者重打
- mod 装错版本、依赖处理不清楚
- 整合包用一段时间后想换版本，要重新折腾

**价值**：
- 选最新 MC 版本，启动器告诉你"23 个 mod 中 18 个支持，5 个等待"
- 一键升级整合包到新 MC 版本，自动备份旧实例
- 缺失的 mod 一旦支持新版，启动器自动通知补装
- 整合包带有 CI 验证 badge，能看到"这个版本被验证过能进游戏"

### 3.3 第三方 UP / 社区

**痛点**：
- 没有低门槛的整合包发布渠道
- 没法触达启动器内的玩家

**价值**：
- 任何 GitHub 仓库可以是一个整合包源
- 玩家添加 URL 即可订阅
- 享受同样的 CI 验证、动态解算能力

### 3.4 MMCL 项目

**价值**：
- 形成 PCL2/HMCL/Prism 都不具备的差异化护城河
- 从"工具"升级成"平台"
- 用米奇喵已有的 2.5 万粉丝渠道做冷启动

## 4. 核心需求

### 4.1 整合包源协议（Schema 层）

整合包源用一个公开可访问的 `manifest.json` 描述：

```
manifest.json (源根)
├── source_name, author, homepage
├── packs[]                              // 这个源里有哪些整合包
│   ├── id, display_name
│   ├── mc_versions[]                    // 声明支持哪些 MC 版本
│   ├── loader（fabric/forge/neoforge）
│   ├── support_level (active/maintenance/archived)
│   └── pack_url                         // 指向 pack.json
│
pack.json (整合包根)
├── id, display_name, version
├── mods[]                               // 只声明 ID，不写死版本
│   ├── source (modrinth/curseforge), id, name
│   ├── policy (auto/lock)               // 自动跟随最新版 / 锁定特定版本
│   ├── criticality (core/optional)      // 是否核心 mod（影响升级判定）
│   └── deprecated_after, replacement   // 弃坑时指定替代品
└── config_overlay                       // 配置文件目录（按 MC 版本分支）
    ├── _common/
    ├── 1.20/
    └── 1.21/
```

**关键决策**：
- 整合包技术 ID 用 MC 数字版本号（`miao-1.21-base`），不用年份
- 显示名可以包含 Drop 名（"米奇喵 1.21 Tricky Trials 基础整合包"）
- mod 列表声明式，版本由启动器解算
- 配置文件按 MC 版本分支 overlay

### 4.2 整合包发现与安装

**GUI 位置**（最终决定）：
- **入口**：在「+ 新建实例」对话框里加「整合包」Tab（候选 B）
- **管理**：在实例详情面板加「整合包同步」Tab（候选 C）
- **未来扩展**：等多源生态成型后，可升级到侧栏一级「发现」入口（候选 A）

**用户路径**：
```
[+ 新建实例] → [整合包 Tab] → [选择源: 米奇喵 ▾] → [选择整合包]
  → [选择 MC 版本: 1.21.5 ▾]
  → [兼容性预览: ✓18 ⚠5]
  → [确认安装]
  → 启动器解算 mod 版本 → 装 loader → 批量装 mod → 写配置 overlay
  → 完成
```

### 4.3 mod 兼容性解算

整合包作者声明 mod 列表，**启动器在用户选定 MC 版本后实时解算每个 mod 的具体版本**。

**Mod 状态分类**（玩家可见）：

| 状态 | 含义 | UI 颜色 |
|---|---|---|
| ✅ Compatible | Modrinth/CF 已有该 MC 版本的发布 | 绿 |
| ⚠️ Pending | 当前不支持，但 mod 仍在维护 | 黄 |
| ❌ Abandoned | 超 6 个月无更新 | 红 |
| ⚠️ Conflict | 有兼容版本但依赖冲突 | 黄 |

**依赖处理**：
- `required` 依赖自动补全（即使作者没列出）
- `incompatible` 直接报警，不自动解决
- 解算策略：贪心 + 回溯（不需要 SAT solver）

**性能要求**：
- 缓存 6-12 小时
- 用 Modrinth 批量接口（`/v2/projects?ids=[...]`）
- 单整合包解算应在 5 秒内完成

### 4.4 跨版本升级流程

**触发**：启动器检测到当前实例对应的整合包有新 MC 版本支持。

**升级对话框需展示**：
- 当前版本 → 目标版本
- mod 兼容性报告（4 类状态分级）
- 升级方式选择：
  - **创建新实例（默认）** —— 安全
  - 原地升级（高级选项，警告强）
- 备份选项
- 是否携带存档（明确警告 mod 数据可能损失）

**升级判定**：
- 看 `core` mod 是否全部支持新版
- `optional` mod 缺失不阻塞升级，标记为 pending
- 全部 `core` 都支持 → 显示"准备就绪"
- 否则显示"等待 X 个核心 mod 更新"

**Pending mod 后续处理**：
- 后台周期检查（每天 1 次）
- 命中后弹 toast：「Iris 已支持 1.21.5，是否补装？」
- 一键补装

**弃坑 mod 替代**：
- manifest 中可声明 `deprecated_after` + `replacement`
- 升级到该版本时启动器自动用替代 mod，提示玩家

### 4.5 CI 验证

**目标**：整合包源仓库有 GitHub Actions，对每个 (pack × mc_version) 组合自动跑验证。

**三阶段策略**：

| 阶段 | 内容 | 时长 | 失败行为 |
|---|---|---|---|
| Stage 1 解算 | 查 API 验证 mod 在目标版本有兼容发布 | 30 秒 | fail |
| Stage 2 安装 | 实际下载 jar、装 loader、检查 mod metadata | 1-2 分钟 | fail |
| Stage 3 Smoke test | Xvfb + probe mode 启动 MC、加载所有 mod、退出 | 5-10 分钟 | warning（避免假阳性） |

**Probe mode**：
- MMCL 内置一个轻量 probe mod
- 监听所有 mod onInitialize 完成
- 输出 `PROBE: ALL_MODS_LOADED`
- 调 `System.exit(0)` 干净退出

**触发**：
- PR 提交时跑（mod 列表改动验证）
- 每天定时跑（捕获 mod 上游破坏）

**CI badge 暴露给玩家**：
```
✅ 1.20.1  最后验证: 2 小时前
✅ 1.21.1  最后验证: 2 小时前
⚠️ 1.21.5  最后验证: 2 小时前 (Iris 加载失败)
```

**MMCL CLI 增量需求**：
- `mmcl-resolver`（解算工具）
- `mmcl new --from-resolved <json>`
- `mmcl mod-install-batch`
- `mmcl launch --probe-mode`

### 4.6 多源 / 第三方源支持

**发布载体**：任何 GitHub 仓库即可，启动器只需要 raw URL。

**信任与安全**：
- mod 必须从 Modrinth/CurseForge 下载（不允许源里塞 jar URL）
- 配置文件可以塞，但首次安装前显示文件列表预览
- 不允许塞可执行文件 / shell 脚本
- 添加非默认源时显示警告："此源未经 MMCL 验证"

**默认源**：
- 米奇喵整合包源（启动器内置）
- 可选：MMCL 官方精选源（作者审核过的）

**用户自添加源**：
- Settings → 整合包源 → 添加源 → 输入 URL
- 启动器拉 manifest，提取作者、首页、整合包列表
- 标记 "未验证" 警示

## 5. 设计原则与取舍

### 5.1 配置文件同步策略

**默认 first-install-only**：
- 首次安装写入推荐配置
- 后续更新**默认不覆盖**用户修改
- 作者显式发布配置更新时，弹对话框让用户选

**给用户"重置为推荐配置"按钮**，但不要默认覆盖。

### 5.2 升级默认走"新建实例"而非原地

- MC mod 生态有大量"跨版本不能继续玩同存档"情况
- 新建实例可预测性最高、回滚成本为 0
- 原地升级作为高级选项保留

### 5.3 离线优先

- 所有 manifest 必须缓存到本地
- 玩家断网时仍能启动已安装整合包
- 后台更新检查不阻塞游戏启动

### 5.4 不让 MMCL 看起来像"米奇喵专用启动器"

- 米奇喵源是首发也是头部，但不是唯一
- UI 设计上确保"任何源平等"
- 文档明确鼓励第三方贡献源

### 5.5 内容信任外包给 Modrinth/CurseForge

- mod 内容来源必须是这两个平台之一
- 启动器不审核 mod 本身的安全性
- 整合包源只控制"装哪些 mod"，不控制"mod 是什么"

## 6. 风险与限制

| 风险 | 缓解 |
|---|---|
| Modrinth `game_versions` 字段不可靠 | mod 状态分级 + CI 双重验证 |
| Modrinth API 速率限制 | 缓存 6-12 小时 + 批量接口 |
| 配置文件随 mod 升级不兼容 | 配置 overlay 按 MC 版本分支 |
| MC 大版本升级损坏存档 | 默认新建实例 + 警告 + 备份 |
| Xvfb 软件 OpenGL 假阳性 | Stage 3 失败标 warning，不阻断发布 |
| 个别 mod 永远不支持新版 | criticality 分级 + 替代品声明 |
| 用户以为 MMCL 绑死米奇喵 | 多源平等 UI + 文档明示 |
| 第三方源恶意 mod | 强制 Modrinth/CF 来源 + 配置预览 + 未验证警告 |

## 8. 与 B 站推广的关系

整合包源生态完成后，米奇喵的 B 站发布动作可以是：

1. **铺垫视频（候选 C 风格）**：「做了个开源 Minecraft 启动器，想听听大家的意见」
   - 不强推下载，主要收反馈
   - 把"beta / 单人开发"预期前置
   - 不消耗强推额度

2. **整合包发布视频（候选 A 风格）**：「可能是最适合 mod 玩家的开源启动器? MMCL + 米奇喵基础整合包一键装」
   - 主打"米奇喵整合包内置 + 自动跟进 + CI 验证"
   - 这是 MMCL 的差异化护城河被外化的时刻

3. **整合包升级视频**：每次大版本（1.21.4 → 1.21.5 等）出来时，演示"启动器自动检测、一键升级、备份旧实例"
   - 作为持续内容素材
   - 同时做 MMCL 推广和整合包推广

**关键时机**：等 0.3 stable + C 模型 MVP 跑完之后（约 22 工作日 + 1-2 个月真实用户验证），再做正式推广视频。

## 10. 名词约定

- **源（Source）**：托管整合包的 GitHub 仓库或类似公开位置，由 manifest.json 描述
- **整合包（Pack）**：源中的一个具体整合包定义，由 pack.json 描述
- **解算（Resolve）**：在用户选定 MC 版本后，根据 mod 声明列表查询 Modrinth/CF 得出每个 mod 的具体版本和兼容性的过程
- **Probe mode**：MMCL 启动 MC 时只跑 mod 加载阶段、不进入主循环、加载完成后干净退出的特殊模式，用于 CI smoke test
- **Pending mod**：在玩家选定的 MC 版本下暂不支持、但 mod 仍在维护的 mod，等待自动补装
- **Criticality**：mod 的关键度标记，影响整合包升级判定（core 必须全部支持才能升级；optional 缺失不阻塞）
- **Config overlay**：按 MC 版本分支组织的配置文件目录，安装时按 `_common/ + <mc-version>/` 合并写入
